# Upstream compatibility research — 2026-10-26

Research date: October 26, 2026 (Asia/Shanghai). This is an upstream evidence snapshot for the 0.2.0 plan, not a claim that the extension has passed compatibility testing.

## Baseline and current targets

The local repository's latest five commits are dated May 13, 2026; `package.json` identifies version 0.1.2, VS Code engine `^1.90.0`, and `@types/vscode` `^1.90.0`. The README config uses the OpenCode V1 MCP shape and the implementation serves legacy HTTP+SSE through `GET /sse` and `POST /message`. These observations come from the local checkout (`package.json`, `README.md`, `src/sseTransport.ts`), not a verified Marketplace artifact.

## Release-blocking OpenCode changes

V2 nests entries under `mcp.servers` and replaces V1 `enabled` with inverse `disabled`. Timeout settings now distinguish startup, catalog, and execution. Existing V1 snippets should be retained only if labeled explicitly as V1. [Official migration guide](https://opencode.ai/v2/docs/migrate-v1/).

V2 remote servers use Streamable HTTP. The pinned 2.1.4 implementation constructs `StreamableHTTPClientTransport`; its remote connection path has no legacy `SSEClientTransport` fallback. Its retry without an added `codemode` query parameter is not a transport fallback. This directly supports the transport mismatch reported in project issue #4; the checked-in `/sse` server cannot satisfy that remote HTTP client. [Pinned MCP client source](https://github.com/anomalyco/opencode/blob/v2.1.4/packages/core/src/mcp/client.ts).

The old OpenCode V1 source does include both Streamable HTTP and legacy SSE clients, which makes old source snippets or search results misleading for V2. [V1 compatibility implementation](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/mcp/index.ts). Implementation should use the pinned V2 path above as the reference.

Proposed **0.2.0 configuration**, after the new `/mcp` endpoint exists:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "jupyter-vscode": {
        "type": "remote",
        "url": "http://127.0.0.1:9123/mcp",
        "oauth": false,
        "protocol": "legacy"
      }
    }
  }
}
```

The server starts enabled by default, so neither `enabled` nor `disabled` is necessary here. `oauth: false` disables OAuth discovery for this unauthenticated local server. The `protocol` field belongs inside the individual server object. It can be omitted because `legacy` is V2's default. [Official V2 MCP documentation](https://opencode.ai/v2/docs/mcp-servers/).

**Do not confuse protocol era with transport.** In this configuration `legacy` means the classic `initialize` handshake and protocol revisions through 2025-11-25, over Streamable HTTP. It does not restore the old `/sse` transport. `auto` probes `server/discover` for revision 2026-07-28 then falls back; explicitly choosing `2026-07-28` requires that revision. The same MCP documentation defines these modes and defaults. Code Mode is also the V2 default, so tests should verify both tool discovery and actual invocation rather than only looking for nine direct provider-native tools.

OpenCode 2.1.4 pins `@modelcontextprotocol/client` and `@modelcontextprotocol/core` to **2.3.1** and uses server 2.3.1 for its development tests. [Pinned dependency manifest](https://github.com/anomalyco/opencode/blob/v2.1.4/packages/core/package.json). Select and lock a server SDK/protocol combination that passes this client's default handshake. Do not blindly follow the MCP `latest` specification: the [2025-11-25 transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) still defines initialize/session-era Streamable HTTP, while the newer era changes lifecycle semantics. Migrating to the newest era is independent of fixing transport compatibility.

For the initialize-era endpoint, acceptance should cover JSON or SSE POST responses, notifications, session routing, termination behavior, and the negotiated protocol header. Keep legacy SSE only as an intentional compatibility surface. The specification permits hosting it alongside the new endpoint. It also requires Origin validation and recommends local binding to localhost. The present unchecked origin and all-interface listener need explicit correction as part of the server rewrite. [2025-11-25 transport requirements](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## VS Code and Jupyter implications

VS Code 1.143 makes the Copilot harness the default for new sessions. Its notes explicitly mention reducing waits caused by MCP servers that do not finish loading tools. This strengthens the case for bounded startup/catalog work and useful diagnostics. The notes do not establish any breaking change in this extension's notebook APIs. [1.143 release notes](https://code.visualstudio.com/updates/v1_143).

VS Code has already supported MCP generally since 1.102, released July 9, 2025; this is older than this repository's last development, not a new October feature. [1.102 release notes](https://code.visualstudio.com/updates/v1_102). Current stable declarations include `lm.registerMcpServerDefinitionProvider`, `McpServerDefinitionProvider`, and `McpHttpServerDefinition`. [Pinned 1.143.1 declarations](https://github.com/microsoft/vscode/blob/1.143.1/src/vscode-dts/vscode.d.ts). Auto-registering this extension's endpoint in VS Code's own MCP client is a possible later enhancement; it is not required to restore OpenCode connectivity, and it requires an engine/API compatibility decision.

The stable notebook API exposes notebook document changes including execution-summary and output changes. A cell's `executionSummary` describes its **most recent execution**; it is not a reliable in-flight kernel state. [VS Code API reference](https://code.visualstudio.com/api/references/vscode-api#NotebookCell). Thus the current success-value polling can return a prior run's results, and its inferred busy/idle result can be wrong. This is a local correctness issue rather than evidence of a new VS Code regression. Execution completion must correlate to the new run and report timeout/cancellation honestly.

Jupyter's public declarations expose `kernels.getKernel(uri)`, `Kernel.status`, and `Kernel.onDidChangeStatus`; use this supported status surface when available. They do not expose the presumed `jupyter.getVariables` command as a public contract. [Jupyter public API declarations](https://github.com/microsoft/vscode-jupyter/blob/main/src/api.d.ts). The current catch-and-empty-array behavior hides unsupported access. Plan a capability-aware variable response and validate the installed Jupyter version; `main` is not proof of a released Marketplace version. Do not depend on proposed APIs solely because source files exist.

## Issue #1: sending a cell to the OpenCode composer

V1 documents `POST /tui/append-prompt`. [V1 server documentation](https://dev.opencode.ai/docs/server/). The pinned V2 OpenAPI has no equivalent `/tui/append-prompt` or draft-composer endpoint. Its `/api/session/{sessionID}/prompt` admits input and normally schedules execution; that differs from appending unsent text to a UI composer. [Pinned V2 OpenAPI](https://github.com/anomalyco/opencode/blob/v2.1.4/packages/protocol/openapi.json).

V2 retains an internal `tui.prompt.append` event, but that alone is not a supported public HTTP operation or discovery contract. [Pinned event schema](https://github.com/anomalyco/opencode/blob/v2.1.4/packages/schema/src/tui-event.ts). Therefore #1 requires a separate integration spike for session/client discovery, authentication, targeting, and draft behavior. An explicit Copy Cell for OpenCode action is a reasonable precursor, but does not complete the requested HTTP composer integration. Do not replace it silently with automatic prompt execution.

## Known upstream issues and limits of this research

- [OpenCode #57675](https://github.com/anomalyco/opencode/issues/57675): V2 missing from GitHub Releases is deliberate distribution behavior, not this extension's bug.
- [OpenCode #21741](https://github.com/anomalyco/opencode/issues/21741): older long-running MCP HTTP timeout report, closed June 22 as completed. Use long-running notebook execution as a regression scenario; do not claim this historical issue remains open.
- [OpenCode #15103](https://github.com/anomalyco/opencode/issues/15103): historical Streamable HTTP Accept-header report, closed. It illustrates why SDK-client compatibility must be tested; it does not establish a current 2.1.4 bug.
- 2.1.4 fixed MCP form presentation/timeouts, but this extension currently exposes tools without elicitation. Avoid adding input-form dependencies to the compatibility release. [2.1.4 changelog](https://github.com/anomalyco/opencode/blob/v2.1.4/CHANGELOG.md).

No complete desktop integration run was performed in this research subtask. Exact Marketplace 0.1.3 contents and Jupyter stable version were not verified here. The strongest release gates are a locked SDK client/server transport test and a real VS Code 1.143.1 + released Jupyter + OpenCode 2.1.4 notebook run. This research supports prioritizing transport/config repair, reliable notebook operations, and the cell inspection request (#2), with #1 composer injection scoped separately.
