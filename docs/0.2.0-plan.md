# OpenCode Jupyter 0.2.0 plan

Reviewed 2026-10-26 (Asia/Shanghai). Status: locally implemented; see [tickets](tickets/README.md) and [validation/release gates](0.2.0-validation.md).

## Release goal

Restore native OpenCode v2 connectivity and make a targeted notebook inspect → edit → execute → inspect-output workflow reliable. Ship the three cell inspection tools requested in #2. Keep the extension usable by other MCP clients and preserve the existing nine tool names.

The first implementation work should address #4. Adding notebook features before fixing the connection would leave current OpenCode users unable to reach them.

## Findings from the current code

These are source-review findings, except where explicitly marked as a probe. They are not claims that every scenario was exercised in VS Code.

| Area | Current behavior | Required change |
| --- | --- | --- |
| Transport | `SseTransport` only routes `GET /sse` and `POST /message`. Probe: `POST /sse` and `POST /mcp` both returned 404. | Implement Streamable HTTP at `/mcp`; retain legacy routes for migration. |
| Response routing | `sessionId` is advertised but ignored on POST; `send()` broadcasts responses to all SSE clients. | Isolate clients and route each response to its requester, including concurrent clients using the same RPC id. |
| Local binding | `listen(port)` omits a host. Probe observed binding to `::`; wildcard CORS is enabled. | Bind explicitly to loopback; validate Host/Origin and remove wildcard browser access. Apply protections to old and new routes. |
| Lifecycle | Manager is assigned before start completes; auto-start checks only active editor; stop is not awaited on deactivation. | Serialize start/stop, handle bind failure/retry and already-open notebooks, dispose connections/listeners reliably. |
| Execution | Completion polling can accept a previous execution summary and silently returns after 30 seconds. | Observe changes belonging to the newly requested execution; report timeout, cancellation and kernel errors explicitly. |
| Notebook edits | Replaces the entire cell to edit source, risking loss of outputs/metadata/identity; ignores `applyEdit`'s result and re-resolves the active notebook after awaiting. | Edit the cell text document, preserve identity and existing notebook data, check edit success, and retain the originally resolved notebook URI. |
| Arguments | Index only checked as a number; insertion kind and URI are largely casts. | Validate integer bounds, enum values, URI types and actual Jupyter notebook type before dispatch. |
| Kernel status | Infers state from historical execution summaries; returns idle even without a proven running kernel. | Use public Jupyter kernel status when available; return unknown/unavailable honestly otherwise. |
| Variables | Calls `jupyter.getVariables`; any failure becomes an empty successful list. | Verify a supported API path; return an explicit unsupported/error result if absent. Do not invent an empty kernel state. |
| Outputs | UTF-8 decodes every MIME, including images, and truncates strings at 10,000 characters. | Preserve MIME and binary encoding, bound payloads and expose truncation information. |
| Version reporting | MCP `serverInfo.version` is hardcoded `0.1.0`. | Derive it from extension/package metadata. |

Source anchors: [extension lifecycle/config](../src/extension.ts), [transport](../src/mcpServer.ts), [MCP dispatch](../src/mcpServer.ts), [notebook adapter](../src/jupyterApi.ts).

## Implementation sequence

### 1. Establish release base and checks

- Reconcile the reported `0.1.3` artifact with repository history; keep any valid published changes when preparing 0.2.0.
- Fix the two baseline lint errors. Add focused test infrastructure and CI for compile, lint and transport/adapter tests.
- Keep the existing `^1.90.0` compatibility target for now. Pin VS Code types to the floor and run a compatibility job with a Jupyter release that supports it. Capability-gate newer integration APIs. If that combination cannot meet the release contract, explicitly revise the minimum and migration notes before release; do not silently imply that latest Jupyter supports VS Code 1.90.
- Select a released, pinned MCP SDK version after checking its Node engine, CommonJS/bundling compatibility and OpenCode v2 interoperability. Bundle runtime dependencies in the VSIX: `.vscodeignore` currently excludes all `node_modules`.

Done when: a clean checkout installs deterministically and has a passing baseline pipeline; the MCP dependency is actually present in a packaged extension.

### 2. Restore native OpenCode v2 connectivity — P0, #4

- Use the official MCP SDK for protocol handling and transport boundaries, keeping the existing notebook adapter and tool names. Avoid expanding the current handwritten JSON-RPC implementation.
- Add `/mcp` Streamable HTTP and preserve `/sse` + `/message` as an explicitly documented legacy compatibility path for 0.2.x.
- Match the protocol supported by the selected SDK and OpenCode client. OpenCode v2's `protocol: "legacy"` refers to the older initialization handshake **over Streamable HTTP**, not to the deprecated HTTP+SSE transport. Do not just advertise the newest protocol date.
- Target initialize-era Streamable HTTP first, using the client's default protocol mode. The July 2026 MCP revision changed initialization/session and GET-stream behavior; adopting that newer era is separate scope. Test the negotiated revision and corresponding request/notification behavior; only advertise revisions the implementation supports. See the [versioning specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) and [current HTTP binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).
- Isolate all request responses and legacy sessions. Reject invalid/expired session identifiers where the selected protocol uses them. Bound request size, handle malformed JSON and methods predictably, and release resources on disconnect/stop.
- Bind to `127.0.0.1`, validate Host and supplied Origin, and accept expected non-browser MCP clients. These checks follow the [MCP transport requirements](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports). Do not expose an unauthenticated public listener.
- Generate v2 configuration from one helper shared by the command and docs tests. Include native `/mcp` and the v2 `mcp.servers` schema; use `disabled`, not v1's `enabled`. Offer a clearly labeled v1 snippet for migration, rather than mixing schemas.
- Implement an explicit stopped/starting/running/stopping lifecycle, bind-error recovery, configured-port validation and actionable diagnostics. Make configuration available before the server is running, using the configured endpoint and a clear stopped status.
- Keep notebook-triggered auto-start. At activation inspect open Jupyter documents, not just the focused editor; also listen for notebook opening. Manual Start works before opening a notebook. Document opening VS Code/the notebook before connecting OpenCode and the verified v2 reconnect procedure. Do not promise retry behavior in an external daemon the extension does not control.
- Declare/test workspace extension placement for Remote-WSL/SSH, with the server running beside the Jupyter extension. Explain that loopback refers to that host; test same-host OpenCode first and document any required VS Code port forwarding for a client on another host.

Done when: installed OpenCode v2 and current stable discover all existing tools directly through `/mcp`, without `mcp-remote`; two clients cannot receive each other's results; a legacy client still connects; stop/start and occupied-port recovery work.

Proposed v2 configuration, usable **after** the new endpoint exists (per the [v2 MCP docs](https://opencode.ai/v2/docs/mcp-servers/)):

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "jupyter-vscode": {
        "type": "remote",
        "url": "http://127.0.0.1:9123/mcp",
        "oauth": false,
        "protocol": "legacy"
      }
    }
  }
}
```

Enabled is the default; the `legacy` protocol field is explicit here to distinguish the initialize-era protocol from the legacy SSE transport. In OpenCode v2's default Code Mode, acceptance means the tools can actually be discovered and invoked; it does not require twelve separate top-level provider tools to appear in the UI.

### 3. Make notebook operations trustworthy — P0/P1, #3

- Centralize notebook resolution: explicit URI always wins; use the active Jupyter notebook or the sole open Jupyter notebook only when unambiguous. Return a useful choice-required error otherwise. Preserve the resolved URI across awaits and focus changes.
- Validate zero-based integer indices and bounds. Reject markdown execution. Check all edit results, use text edits for source replacement, and preserve metadata/output/identity.
- Subscribe to stable notebook changes before requesting execution and correlate fresh execution-summary/output changes with the target cell. Verify command signatures against the supported VS Code versions. Clean listeners on completion, timeout, close and cancellation. If a reliable fresh completion cannot be established, return an explicit indeterminate outcome instead of stale success.
- Serialize execution requests per notebook as needed; handle kernel selection prompts, restart during execution, interrupted work, execution failures, empty outputs and long-running cells. Choose/document a configurable execution timeout; MCP client tool timeout must exceed it.
- Activate and inspect the installed Jupyter extension's public exports. Its [kernels API](https://github.com/microsoft/vscode-jupyter/blob/main/src/api.d.ts) exposes kernel status and status events for kernels already started by the user. Normalize this into the existing status tool's contract and return unknown with a reason if there is no accessible kernel.
- Verify restart behavior in the extension host, especially for an explicitly targeted inactive notebook. For variables, use only a verified supported path; preserve the existing tool name and return `isError` with an actionable unsupported message when the installed extension lacks it. Do not introduce silent code injection into arbitrary-language kernels.

Done when: a rerun waits for new execution, a timeout never reports completion, editing preserves notebook data, and explicit notebook targeting remains correct while focus changes.

### 4. Add targeted cell inspection — P1, #2

Add `jupyter_list_cells`, `jupyter_read_cell_input` and `jupyter_read_cell_output`, retaining `jupyter_get_notebook` for compatibility.

| Tool | Input | Result contract |
| --- | --- | --- |
| `jupyter_list_cells` | Optional notebook `uri`; optional bounded pagination | Notebook URI/version and cells with `cell_id`, zero-based index, kind, language and nullable execution order. No full source or outputs. |
| `jupyter_read_cell_input` | Optional notebook `uri`; required `cell_id` | Source, language, kind, current index and notebook version. |
| `jupyter_read_cell_output` | Optional notebook `uri`; required `cell_id`; optional bounded output selection | Grouped output items with MIME, explicit text/base64 encoding, byte counts, execution summary and truncation metadata. |

- Use the cell document URI as an opaque identity scoped to the current open notebook; use a persisted nbformat ID only if its availability and preservation through the VS Code serializer are verified. Never treat the numeric index as a stable ID. Return cell-not-found for a deleted/reopened invalid identity, and document the lifetime.
- Preserve notebook URI support, including remote and untitled URIs. Do not turn these tools into arbitrary filesystem reads. Document the mapping from #2's proposed `notebook_path` to the extension's existing URI convention.
- Text/error outputs remain readable; supported images are returned as valid MCP image content when requested and within limits. Other binary MIME types retain a lossless base64 representation or a clear omitted/unsupported descriptor. Do not return broken partial image data.
- Use bounded defaults (proposed: 100 cell descriptors per page and 256 KiB aggregate output per read) with explicit cursors/limits and truncation indicators. Keep metadata in the text result even when an MCP image item is also returned. Mark genuinely read-only tools with appropriate annotations.
- Preserve old result fields where feasible. Document any necessary correction to binary output encoding so existing users can migrate deliberately.

Done when: an agent can list cells and inspect one cell's input/output without receiving the entire notebook, handles a PNG/error/large output correctly, and still finds the same live cell after cells are inserted above it.

### 5. Documentation, packaging and release

- Replace README quick start and generated configuration together. Show native OpenCode v2 first and label v1/legacy instructions separately. Include startup/reconnect, custom port, WSL/SSH, multiple windows/port conflicts and unsupported-kernel diagnostics.
- Reconcile source/package/MCP server version reporting, update the lockfile and create a 0.2.0 changelog. Verify publisher identity and packaged runtime dependencies; exclude research notes, sample notebooks and development artifacts from the VSIX where appropriate.
- Publish a prerelease/test VSIX for the full workflow before a stable Marketplace release. Record exact OpenCode, VS Code, Jupyter, MCP SDK and negotiated protocol versions in release validation.
- Proposed GitHub follow-through during implementation: use #4 and #2 for the main work, add a focused reliability/testing issue under #3, and record the v2 draft-API limitation on #1. This planning pass does not post comments or modify issues.

## Validation and release gates

| Layer | Required evidence |
| --- | --- |
| Build/package | Clean install, compile, lint, focused automated tests and VSIX install succeed; runtime SDK loads from the packaged extension. |
| Transport | Actual MCP client initialization/discovery/tool call for supported revisions; notifications/HTTP errors; malformed inputs; parallel clients with identical RPC ids; client disconnect; repeated start/stop; occupied port; Origin/Host and loopback checks; legacy SSE regression. |
| Notebook adapter | Two open notebooks and changing focus; source edit metadata/output preservation; invalid indices; failed edit; first run/rerun; error output; timeout; interrupted/restarted/missing kernel; removed cell; binary and large outputs. |
| Host compatibility | Current VS Code stable + current compatible stable Jupyter, and declared minimum VS Code with a compatible Jupyter version. Insiders smoke is informative, not a reason to block on unrelated upstream defects. |
| OpenCode | Installed `2.0.26`, current `2.1.4` (or newly verified stable at implementation), and the issue's `2.0.21` if obtainable. Validate generated configuration with the actual parser/client. Test v1 separately for the promised migration path. |
| Remote | Linux local and Remote-WSL are required because #4 reports WSL. Add Windows/macOS desktop smoke coverage before claiming those environments verified; SSH gets the same-host smoke plus documented connection placement. |
| User workflow | Fresh VSIX → open/select kernel → obtain config → connect OpenCode → discover notebook → list/read cell → edit → run → inspect new output/error → stop/restart server → reconnect. Repeat with explicit URI on an inactive notebook. |

No stable release until native v2 connection, correct targeted execution, client isolation, and the new cell reads pass. Existing kernel tools must return either verified results or explicit unsupported errors, never fabricated successful state. Tests must exercise transport and host boundaries, not only mocked tool dispatch.

## Scope boundary and ordering

Core 0.2.0 contains steps 1–5. Implement in reviewable slices: baseline → transport/config/lifecycle → notebook correctness → cell inspection → release verification. Reliability tests accompany the slice that changes the behavior. If only one slice can be tackled first, choose transport/config/lifecycle for #4.

Full #1 draft injection, custom mention pills, multi-cell batching, automatic edits to users' OpenCode configuration, a separate notebook host, public MCP hosting, MCP Apps and Copilot-specific integrations stay outside this release. VS Code already has native notebook/AI features; the value here is dependable access from OpenCode and other external MCP clients.

An optional clipboard command may format notebook URI, cell identity, language and source for manual pasting. It must be named and documented as copying context, leave the clipboard untouched on failure, and must not silently submit a session message or claim that an OpenCode draft was updated.
